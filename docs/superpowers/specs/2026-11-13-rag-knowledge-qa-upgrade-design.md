# RAG 智能知识问答系统升级设计

## 1. 背景与意图

当前仓库是一个以 `FAQ.txt`、LlamaIndex 和 DashScope 为核心的命令行原型，已有 FAQ 解析、索引构建、查询和部分备份管理代码，但尚未形成可部署的后端系统。现有实现还存在职责耦合、配置硬编码、Faiss 接入不完整、异常处理不一致以及若干明显逻辑错误。

本次升级将项目重构为模块化单体后端，使它能够真实支撑简历中描述的 RAG 知识问答场景，并保留继续演进为更复杂 Agent/RAG 平台的空间。项目文档必须明确区分“已经实现并验证的能力”“需要真实数据才能复现的指标”和“后续路线图”，不能把目标指标伪装为当前实测结果。

## 2. 目标

- 提供 FastAPI REST API 和基于 SSE 的流式问答接口，并自动生成 OpenAPI 文档。
- 支持 TXT、Markdown 和 JSON 文档上传、解析、分块、索引及状态查询。
- 实现自适应文本分块：根据文档类型和长度选择 Chunk Size，并使用重叠窗口保留上下文。
- 实现向量检索与关键词检索双路召回，通过可配置的 Reciprocal Rank Fusion（RRF）合并排序。
- 基于策略模式组织 Agent，首个策略实现上下文问答；为 Plan-and-Execute 预留稳定接口，但不虚构其已完成。
- 提供多轮会话记忆、Prompt 模板管理和可追踪的检索/生成链路信息。
- 实现三级模型降级：主模型、备用模型、检索摘要兜底；各级切换有结构化日志和响应元数据。
- 建立可重复的检索评测工具，支持 Hit@1、Recall@K、MRR 和问答准确率输入/输出，但不伪造“200 条、85%+”结果。
- 生成项目 Logo 和架构图，存放在 `docs/image`，并编写一份与实际实现一致、强调开发预览状态和升级路线的中文 README。
- 补充单元测试、API 测试、示例环境配置和可本地运行的无外部密钥测试路径。

## 3. 非目标

- 本阶段不开发 Web 管理端或聊天页面。
- 不拆分微服务，不引入消息队列、Kubernetes、多租户、RBAC 或完整监控平台。
- 不实现完整 Plan-and-Execute 推理引擎，只定义策略契约和扩展点。
- 不承诺或伪造当前仓库尚未通过评测得到的业务指标。
- 不将生产密钥、真实用户文档或内部服务地址提交到仓库。

## 4. 反目标

- 不能只新增一个 FastAPI 壳层、继续把业务逻辑堆在旧脚本中。
- 不能让上传接口阻塞式完成不可控时长的索引重建而没有任务状态。
- 不能将 LLM 回答当成唯一结果而不返回来源引用或降级状态。
- 不能让单个模型或外部 API 故障导致所有问答接口不可用。
- 不能用 README 宣传尚未实现或未验证的能力。

## 5. 约束与默认决策

- 继续使用 Python、FastAPI、LlamaIndex、Faiss 和 DashScope，与已有技术栈保持一致。
- 采用模块化单体，进程内完成文档摄取、检索、Agent 编排和模型路由。
- 默认数据持久化仍使用本地文件：Faiss 索引、文档清单、会话和任务元数据分目录保存；接口抽象允许后续替换数据库。
- 索引构建任务先使用 FastAPI 后台任务与进程内任务注册表，明确单进程限制；后续路线图再迁移持久化队列。
- 测试不得依赖真实 DashScope 密钥。Embedding、LLM 和时钟必须可注入，测试使用确定性假实现。
- 保留旧 FAQ 数据作为示例迁移输入，但旧脚本不再作为正式运行入口。
- `docs/image` 使用用户指定的目录名；Logo 采用可版本控制的 SVG，架构图也优先使用 SVG。

## 6. 已考虑的方案

### 方案 A：模块化单体（已选择）

将 API、文档摄取、检索、Agent、模型路由、会话和基础设施拆成清晰模块，但作为一个 FastAPI 服务部署。它能在当前规模下保持低运维成本，同时提供足够明确的扩展边界和测试面。

### 方案 B：在现有脚本上增量扩展

修改量较小，但会继续放大全局 LlamaIndex Settings、文件操作、索引管理和 API 层之间的耦合。混合检索、任务状态、降级和评测难以独立测试，因此未采用。

### 方案 C：服务化拆分

把摄取、检索、Agent 和模型网关拆为独立服务，扩展性更强，但当前项目缺乏相应规模和运维基础。它会把工作重心从 RAG 质量转向分布式基础设施，因此留作远期方向。

## 8. 核心设计

### 8.1 文档摄取

- 上传接口接收 `.txt`、`.md`、`.json`，校验扩展名、MIME、大小和空内容。
- Parser Registry 按格式选择解析器；JSON 支持 FAQ 数组（`question`/`answer`）、顶层 `text`/`content` 字段以及包含这些字段的对象数组。JSON 的语法和顶层结构在创建任务前完成轻量校验，无法识别时直接返回明确的 422；完整解析、分块和索引仍在后台执行。
- 解析结果统一为带 `document_id`、来源、标题、段落位置和原始元数据的内部文档模型。
- 自适应分块器根据文档长度、标题层级、段落边界和格式选择目标大小。初始默认区间为 256–768 tokens，重叠约为目标大小的 10%–20%，配置可覆盖。
- 分块优先尊重 Markdown 标题和自然段；过长段落才按句子与 token 窗口切分。
- 摄取创建任务并立即返回 `202 + task_id`；任务记录在返回前持久化，后台执行解析、分块、Embedding、向量写入、关键词索引更新和清单提交。单进程重启后，遗留的 `pending`/`running` 任务标记为可重试失败，不自动猜测执行到哪一步。
- 索引写入采用临时版本后原子切换，失败时保留上一可用版本。
- 删除也作为异步索引变更任务返回 `202 + task_id`；只有新索引、文档清单与原始上传文件的删除完成原子发布后，任务才标记成功。已有会话中的历史引用元数据保留，但不保留被删文档的完整片段正文，并标记来源已删除。

### 8.2 混合检索

- `VectorRetriever` 使用 Faiss 返回候选及归一化相似度。
- `KeywordRetriever` 在本地分块语料上实现 BM25 风格打分；中文初版使用字符 n-gram/可配置分词适配器，避免把英文空格分词假设用于中文。
- 两路各自取 `candidate_k`，RRF 使用稳定 chunk ID 合并并去重；最终返回 `top_k`。
- 检索、融合和评测的最小相关性单元统一为 chunk。Chunk ID 由文档内容摘要、规范化来源标识、分块策略版本和块序号稳定派生；最终展示阶段可按 document 聚合相邻引用，避免同一来源淹没结果。
- 结果携带来源、分块位置、各路排名、融合分数和文本摘要，便于引用和调试。
- 支持 `vector`、`keyword`、`hybrid` 三种检索模式，以便评测与故障降级。

### 8.3 Agent 与会话

- `AgentStrategy` 定义 `run()` 和 `stream()`，输入包含问题、会话历史、检索配置和请求上下文。
- `ContextualRAGStrategy` 执行查询改写（可关闭）、混合检索、Prompt 构建、模型生成和引用装配。
- 策略注册表通过配置选择当前策略；`PlanAndExecuteStrategy` 只保留协议/文档占位，不注册为可用能力。
- 会话包含稳定 `session_id`、消息序列、创建/更新时间和可选元数据；按最大轮数/字符预算裁剪上下文。
- 每个回答保存用户问题、回答、引用、模型层级、耗时和错误摘要，不保存密钥或完整异常堆栈到 API 响应。

### 8.4 Prompt 管理

- Prompt 使用仓库内版本化模板文件和注册表管理，不散落在业务代码中。
- 模板声明名称、版本、变量和用途；启动时校验必需变量。
- 默认模板要求模型仅依据上下文作答、不确定时明确说明，并输出可映射到引用的标识。

### 8.5 三级降级

1. 主模型：正常流式生成。
2. 备用模型：主模型发生超时、限流、服务错误或配置不可用时切换；无效请求等不可重试错误不盲目降级。
3. 检索摘要兜底：模型均不可用时，返回基于最高排名片段的模板化摘要和引用，不声称这是模型生成答案。

路由器为每次调用设置超时和有限重试，记录 `provider_tier`、降级原因、耗时与 request ID。SSE 在生成开始前失败可以切换模型；输出 token 后失败则发送结构化 `error`/`done` 事件，不能拼接另一个模型的回答造成语义混乱。

降级覆盖完整问答链路，而不只覆盖生成：查询改写不可用时直接使用原问题；Embedding 查询失败时切换为关键词检索；主、备生成模型都不可用时仍返回关键词检索摘要。备用模型允许配置为不同 Provider，以避免同一供应商级故障；若未配置跨 Provider 备用模型，系统也必须保留不依赖模型与 Embedding 的关键词兜底。Embedding 不可用时新文档摄取任务明确失败，不能产生只有半套索引的版本。

### 8.6 SSE 协议

事件类型：

- `meta`：request ID、session ID、检索模式。
- `retrieval`：引用元数据和检索耗时，不暴露不必要的全文。
- `token`：增量文本。
- `fallback`：发生降级时的层级和安全原因码。
- `error`：流中错误码和用户可读信息。
- `done`：最终引用、模型层级、总耗时和完成状态。

服务同时提供非流式问答端点，复用同一 Agent 逻辑。

流式请求在开始时持久化用户消息。只有收到完整模型结果并发送成功 `done` 后，助手正文才进入下一轮 Prompt；中断或失败的流保存状态、已发送字符数和错误原因用于审计，但部分正文默认不进入后续上下文，避免把残缺回答当作事实。

## 9. API 范围

建议首版端点：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/api/v1/documents` | 上传并创建摄取任务 |
| `GET` | `/api/v1/documents` | 查询文档清单 |
| `GET` | `/api/v1/tasks/{task_id}` | 查询摄取任务状态 |
| `DELETE` | `/api/v1/documents/{document_id}` | 删除文档并更新索引 |
| `POST` | `/api/v1/retrieval/search` | 调试检索结果 |
| `POST` | `/api/v1/chat/completions` | 非流式问答 |
| `POST` | `/api/v1/chat/completions/stream` | SSE 流式问答 |
| `GET` | `/api/v1/sessions/{session_id}` | 查询会话摘要与历史 |
| `DELETE` | `/api/v1/sessions/{session_id}` | 删除会话 |
| `POST` | `/api/v1/evaluations/retrieval` | 以 multipart 上传 JSONL 并运行检索评测 |
| `GET` | `/health` | 存活与依赖状态 |

统一错误模型包含 `code`、`message`、`request_id` 和可选 `details`。成功响应不强制套无意义信封，优先保持资源化 API 和明确 HTTP 状态码。

## 10. 评测设计

- 评测集使用 JSONL，每条至少包含 `query` 和相关 `document_id`/`chunk_id`，可选参考答案。
- 首版评测 API 接收 JSONL 文件、检索模式、`top_k` 和可选数据集名称，返回同步小规模评测结果；同一运行器同时提供 CLI，较大数据集建议使用 CLI。人工问答标签通过 JSONL 的可选字段输入，不另建标注后台。
- 检索指标：Hit@1、Recall@K、MRR；分别运行 vector、keyword、hybrid，输出配置快照以保证可复现。
- 问答准确率不默认由同一个生成模型自评。首版支持人工标注结果导入和可选 evaluator 接口。
- 仓库提供小型示例数据集用于验证评测工具，不将它冒充 200 条业务评测集。
- README 将“73% → 85%+、相对提升约 12%”标为目标/简历背景；只有用户补充真实 200 条数据并成功运行后，才可改为可复现的实测结论。

## 11. 可观测性与安全

- 使用结构化日志，至少包含 request ID、session ID（可哈希）、task ID、阶段、耗时和降级层级。
- 不记录 API Key、完整 Prompt、用户上传全文或模型原始敏感错误。
- 上传文件采用服务生成的 ID 和受控目录，禁止使用客户端文件名拼接路径。
- 配置通过环境变量和 `.env.example`；`.env` 保持忽略并检查历史中不引入新密钥。
- 健康检查区分应用存活与外部模型/索引就绪状态。
- 首版部署边界是开发机或受信任内网单用户服务。由于本阶段不实现认证、授权和租户隔离，README 必须明确禁止将服务裸露到公网；生产接入需要外部网关完成认证、TLS、限流和上传大小限制。

## 12. 测试与验收

- 单元测试覆盖三种解析器、自适应分块边界、RRF、中文关键词检索、会话裁剪、Prompt 校验和降级判定。
- 集成测试覆盖上传任务、索引切换、混合检索、非流式问答、SSE 事件顺序、删除文档和错误映射。
- 使用确定性 Fake Embedding 与 Fake LLM，确保无密钥环境可运行完整测试。
- 至少提供一个本地 smoke 流程：启动 API、上传示例文档、等待任务完成、执行检索、完成非流式与流式问答。
- 验收时运行测试、静态检查（若引入）、README 命令和 smoke 流程，并把可复现命令写入文档。
